工程細節：模型技術矩陣

模型 核心架構 / 推論路徑 Zero-shot clone 訓練 / Fine-tune 狀態 手機部署觀察
IndexTTS2 大模型式 TTS / voice cloning pipeline。reference audio 進 speaker/style conditioning，再根據文字生成語音。 可以。它目前最適合當「原版老師」做聲音品質上限。 本機主要用推論和 clone；尚未整理成可重跑的完整訓練線。 品質高，但直接離線塞手機風險大：模型體積、RAM、冷啟動、生成延遲都可能不理想。
CosyVoice2 大型多模組 TTS，適合 text prompt + prompt audio 的高品質生成。 可以。先前 golden teacher 就是從 CosyVoice2 audition 挑出來。 本機有 cosyvoice/bin/train.py，可訓練，但工程成本和資源成本較高。 適合當 teacher / corpus generator；直接手機端部署不務實。
F5-TTS Flow matching 類 zero-shot TTS。文字 + reference 經 acoustic flow 生成語音特徵。 可以，而且是它的強項之一。 目前有 clone audition 和資料痕跡，但還不是本專案主訓練線。 手機端要看模型大小與 runtime；比 teacher 輕，但仍可能偏重。
GPT-SoVITS 兩階段：S1 GPT/semantic token，S2 SoVITS/acoustic/vocoder；也有 LoRA 微調路線。 可以做 zero/few-shot，也可進一步 fine-tune。 本機有 s1_train.py、s2_train.py、s2_train_v3_lora.py。 訓練方法成熟，但手機 runtime 和模型拆分要再評估。
ZipVoice Flow-matching TTS。文字 / prompt conditioning → 多 step acoustic sampling → vocoder。 可以，但本專案聽感穩定性較不如 IndexTTS2 / CosyVoice2。 本機有 train、fine-tune、distill：train_zipvoice.py、train_zipvoice_distill.py。 ONNX/int8 + Sherpa runtime 是手機路線；問題是降到 3/4-step 後容易雜訊或字跑掉。
Piper / VITS VITS 單聲音 TTS：phoneme/text encoder、duration/alignment、flow、decoder/vocoder 端到端出 wav。 不算。通常要為單一聲音訓練或 fine-tune。 已完成 IndexTTS2 teacher corpus 的 10000-step 長訓。 最有機會小、快、離線；代價是語氣自然度、情緒與 clone 還原度可能明顯輸 teacher。
Matcha-TTS 非 autoregressive / flow-matching text-to-mel。生成 mel 後接 HiFiGAN / BigVGAN 類 vocoder。 標準流程不算。除非另外加 speaker conditioning 或訓練單聲音。 正在跑 IndexTTS2 teacher corpus 的 10000-step 長訓，目前約 7080 / 10000 steps。 理論速度好；實際要看 vocoder、duration/phoneme 表現和中文清晰度。
Fish Speech 語音生成 / clone 類模型，常見路線偏 codec/token-based generation。 可以研究，值得補測。 目前未整理成本機主訓練流程。 可能是下一輪 survey 候選；要先確認授權、模型大小、runtime。

工程細節：目前資料與訓練 Pipeline

1. Reference 清理 從下載音檔切女生片段，排除男聲、配樂、唱歌、重疊說話，轉成乾淨 16k/24k wav。
2. Teacher 生成 用 IndexTTS2 / CosyVoice2 讀 reference，對 500 句日常文本生成 teacher wav。
3. Dataset Manifest Piper 轉 phoneme ids / LJSpeech-like 格式；Matcha 轉 pinyin/text-mel filelist；ZipVoice 轉 TSV / fbank。
4. Student Training Piper/VITS 學單聲音端到端 wav；Matcha 學 text-to-mel；ZipVoice 學 acoustic flow / prompt behavior。
5. Export / Runtime 目標是 ONNX/int8 或 native runtime；手機 app 只載一次模型，後續走 cached speaker/reference。
6. Evaluation 同句比較 teacher vs student：字準、音色、台灣腔、尾音、生成時間、peak RSS、模型大小。

工程細節：目前最該追的問題

品質瓶頸 Piper 可能過度平均化，Matcha 可能 text-to-mel 清晰度不足，ZipVoice few-step 可能 sampling trajectory 崩掉。這三種問題表現不同，不能只看 loss。
速度瓶頸 手機端真正瓶頸通常不是 checkpoint 大小本身，而是 acoustic sampling steps、vocoder、runtime backend、threading、冷啟動、reference encoding 是否每次重算。
評估方式 每個候選模型要用相同文本、相同輸出格式、已載入模型後的 warm inference time、peak RSS、檔案大小，以及主觀聽感分數。原版 teacher 必須一起列。
下一步 Matcha 跑完後，先不急著包 app；先匯出 Piper/Matcha 樣本，和 IndexTTS2 原版同句比較。如果 Piper 聲音太死、Matcha 講不清，才回頭調資料或換 student 架構。

一句話結論

現在最務實的路徑：用 IndexTTS2 或 CosyVoice2 當高品質老師，產乾淨語料；再用 Piper/VITS 或 Matcha-TTS 訓練單一聲音小模型；最後跟原版老師做同句對比，選出能塞進紅色蝴蝶結 app 的版本。
