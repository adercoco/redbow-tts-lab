ZipVoice 4-step 優化報告

目標是保留你覺得已經不錯的 4-step 聲音，同時把手機包體變小、峰值記憶體降一點，並用很保守的音訊清理改善刺耳感。這份報告把模型變小、vocoder 量化、後處理清理分開聽。

目前主推包體約 137MB
比原 4-step 包少約 39MB
qint8 vocoder 新測1.63-2.00s / 句
新測 peak RSS約 0.88GB

結論

我現在會把手機候選改成 ZipVoice 4-step int8 decoder + qint8 Vocos + mild clean。它不是重新訓練的新模型，但包體直接從約 176MB 降到約 137MB，這次 Mac CPU 新測單句約 1.6-2.0 秒，聲音音量和低頻髒感也比較容易控制。

乾淨度這件事要分兩層：後處理可以修音量、低頻、刺耳峰值；如果是咬字本身跑掉、電子音、韻律怪，那要回到訓練資料、few-step distillation loss、或 decoder 架構處理。

另外 app 裡目前有一包 CosyTinyTrueDistillInt8 只有約 54MB，但那不是你這次覺得不錯的完整 ZipVoice 4-step。54MB tiny 版先前 ASR gate 沒過，所以它只能算小模型研究線，還不能當主力聲音。

我做了哪些優化

動作 實際做法 它能改善什麼 它不能改善什麼
vocoder 量化 把 vocos_24khz.onnx 換成 vocos_24khz_dynamic_qint8.onnx。 包體少約 39MB，這次 Python ONNX 測試 RSS 也比較低。 ZipVoice decoder 本體還是 119MB，咬字錯誤不會因為 vocoder 量化自動修好。
mild clean 去 DC、65Hz-10.5kHz band-pass、很輕的 soft limiter、RMS 對齊到約 -20dBFS。 音量一致、低頻濁感下降、峰值比較不刺。 不能把錯字變正確，也不能讓韻律更像老師。
spectral gate STFT 後用每個頻段低分位能量當噪聲底，小幅扣掉再重建。 可能讓背景電子底噪更少。 有機會吃掉尾音和氣音，所以我不會直接當主推。
int4 try 測試 decoder 壓縮到約 69MB 的 ONNX 候選。 包體有機會進一步降到 100MB 以下。 如果 runtime 沒有高效 int4 kernel，速度不一定變快，聲音也可能變髒。

下一步

優先序 項目 原因
1 把 app 內建 vocoder 換成 qint8 Vocos 這是最確定的包體收益，聲音若本頁聽起來可接受，就能直接進 app。
2 在 app runtime 加 mild clean 成本低，能穩定音量和降低髒感，但要避免過度降噪。
3 int4 decoder 手機實測 如果 iPhone runtime 真的吃到 int4 加速，才值得繼續；否則只是小一點但不一定快。
4 更乾淨的 few-step distillation 若 4-step 的髒感來自模型生成本身，需要在訓練 loss 和資料篩選處理，不是靠後處理硬救。
